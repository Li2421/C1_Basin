# 二、论文定位、现状与本轮目标

**论文定位（用户确定）：** 修正黑盒 controller 在安全层下出现的死锁，不论死锁成因。黑盒指方法不依赖 controller 的控制律式子，只探查它的行为。死锁是否被解决，用成功率相对 safety baseline（只加安全投影、不加修正）的提升来衡量。timeout 不得直接称为 deadlock。

**现状：**
- 修正对没见过的学习型 controller 零样本有效：三种行为克隆策略只加安全投影时 0–7%，用时间表后 90–97%（round38，CONFIRMATORY）。
- 但选择模型从来没有跨类型起作用。round27、33、38 的选择模型结果都与"一律时间表"完全相同，原因已查清：
  1. 行为指纹（R5-PCA2）是 round16 只用流匹配策略拟合的，最佳修法不同的 controller 在指纹里重叠；
  2. 训练时留出 controller 的负对数似然从第 500 步起一路上升，最后选中最早的 checkpoint，模型只学到了平均最好的臂；
  3. 训练集只有 3 类 controller，而 round15 已经发现，同一配方的不同 seed 几乎是重复样本，有效样本数约等于类型数。
- 学习型类型之间确实有可选的差别：
  - 按进度切换时间表在确定性行为克隆策略上比按比例切换时间表平均高约 4.7pp；
  - 全程 η13 在不同实例之间从 0% 到 98% 不等；
  - η 切换时刻的最佳值随 controller 不同，从第 100 步到第 500 步。
  因此，即使只看学习型 controller，"每个 controller 选自己的切换方式"也比"一律前 500 步 η13"有提升空间。

**本轮目标：**
1. 建一个**学习型 controller 动物园**：类型足够多、训练方式足够不同，使"见过很多种"成立。
2. 做出一条零样本选择 pipeline：只探查新 controller 的行为（不看成败），就为它选修法。在**开发类型的留一类型检验**中，它要明显好于"一律按比例切换时间表"，并接近每个 controller 的事后最佳。
3. 画出"训练类型数对留出遗憾"的规模曲线，回答"见得越多，泛化越好"是否成立。
4. 最后在**锁定类型**上只评估一次。

# 六、pipeline 的开发

**选择的输入与输出：** 输入只有探测特征（以及可选的 R5-PCA2）；输出是为该 controller 选的一个臂。不允许使用任何该 controller 的成败标签（零样本）。少量标签版本单独作为基线。

**训练目标：** 对每个源 controller 和每个臂，用评估标签下界的成功率作为目标。建议以"预测每个臂相对按比例切换时间表的成功率差，再取预测最高的臂"为起点（回归到相对差，而不是对最佳臂做分类，可以减少近似平局的噪声）。

**留一类型开发检验（DEVELOPMENT，8 个开发类型 → 8 折）：**
- 每折留出一个开发类型，在其余 7 个类型上训练（包括特征标准化等全部预处理），在留出类型的评估 state 上打分；
- **controller 等权、类型等权**两种合并方式都报告，主看类型等权（避免流匹配策略的 14 个实例主导）；
- 模型的超参数与训练步数只能在源类型内部再做一次留一类型（嵌套）来选，不得用留出类型的标签选；round38 的教训是留出负对数似然从第 500 步起上升，必须监控并报告。

**起点与可尝试的方向（不限于此，全部记入迭代日志）：**
1. 岭回归，每臂一个，输入为标准化的特征 1–8；
2. 深度 ≤ 3 的回归树或梯度提升树（叶子至少 3 个 controller）；
3. 在特征空间中按最近的 k 个源**类型**（不是实例）加权平均各臂成功率差；
4. 两级结构：先判断"η13 的好处出现在早期还是后期"，再选切换时刻；
5. 对选出的臂加保守约束：若预测优势小于源类型留一误差的 1 倍标准差，就退回按比例切换时间表。

**对照方法（与 pipeline 同表报告）：**
- 一律按比例切换时间表；一律按进度切换时间表；每个臂"一律用它"；
- round38 扩展选择模型（直接使用冻结版本，不重训）；
- 只用 R5-PCA2 的同结构 pipeline（检验"换特征"本身的作用）；
- 少量标签基线：在 8 臂中按前 k 个调参 state（k ∈ {2, 4, 8}）的成功数选，平局取按比例切换时间表；
- oracle（特权）：每个 controller 事后最佳臂，按评估 state 奇偶交叉拟合与样本内两种；另报"每类型最佳固定臂"。

**开发目标（达到就可以冻结；达不到也要在预算内冻结当前最好的版本，并如实报告）：**
- 类型等权合并：pipeline − 一律按比例切换时间表的配对 CI 下界 > 0；
- 相对交叉拟合 oracle 的平均遗憾 ≤ 2pp；
- 没有任何留出类型比一律按比例切换时间表差 3pp 以上；伤害数（比 safety baseline 低 ≥ 10pp 的 controller 数）为 0。

**规模曲线（DEVELOPMENT）：** 冻结的 pipeline 结构固定后，训练类型数 m ∈ {1, 2, 3, 5, 7}：对每个留出类型，从其余 7 个类型中随机抽 m 个（每个 m 抽 20 组，种子开工时写定；m = 7 只有一组），重新训练，记录留出遗憾。画出 m 对平均遗憾（类型等权，带 CI）的曲线，并与"实例数不变、只增加同一类型的实例"的曲线对照（检验"有效样本数约等于类型数"）。

# 七、冻结与锁定类型的评估（CONFIRMATORY）

1. 用全部 8 个开发类型训练最终 pipeline，把代码、特征定义、模型参数、回退规则写入 `FROZEN_PIPELINE.json` 并留 UTC 与 sha256 收据。冻结后不得再改。
2. 锁定类型：checkpoint 选择与能力门（只记通过与否）→ 机制探测 → 用冻结的 pipeline 选臂并留收据 → 再跑评估标签与调参 state 标签。收据时间必须早于这些标签的第一个提交。
3. 只评估一次，报告以下终点：

| 编号 | 检验内容 | 判定标准 |
|---|---|---|
| 锁定终点 1 | 修正在锁定类型上是否有效 | 每个锁定类型：按比例切换时间表 − safety baseline 的配对 CI 下界 > 0 |
| 锁定终点 2（主） | 零样本 pipeline 是否胜过一律时间表 | 两个锁定类型合并（类型等权）：pipeline − 一律按比例切换时间表的配对 CI 下界 > 0；另报每个锁定类型各自的结果 |
| 锁定终点 3 | 是否接近事后最佳 | 相对交叉拟合 oracle 的平均遗憾 ≤ 3pp，伤害数为 0 |
| 锁定终点 4（描述性） | 锁定类型的偏好与机制 | 每个锁定类型的最佳臂；特征落在开发类型范围之外的比例；nominal only → safety baseline 的逐条转移表；强化学习策略是否在安全层下死锁、卡住时是严格冻结还是在动但不前进 |

若锁定 1 的强化学习策略大多"只加安全投影就 ≥ 98%"，就如实报告"在训练中见过其他机器人的强化学习策略在安全层下很少死锁"，锁定终点 2 只按锁定 2 判定并注明。

**CI：** 按共同协议第四节，先在 controller 层重抽，再在 state 层成簇重抽，5000 次，配对；unknown 按下界计，另报上界。类型等权合并时，先在类型层重抽。

# 八、结论映射

| 观察结果 | 结论 |
|---|---|
| 开发目标与锁定终点 2 都达到 | 跨学习型类型的零样本选择第一次做出来了：只探查行为，就能为没见过的学习型 controller 选出比一律时间表更好的修法 |
| 规模曲线随 m 单调下降，且比"只加实例"的曲线下降快 | "见得越多，泛化越好"成立，下一步是扩大动物园（含以后加入的非学习型类型） |
| 开发目标达到，锁定终点 2 不达到 | pipeline 在开发类型之间泛化，但没能外推到差别更大的学习方式；看锁定类型的特征是否落在开发范围之外 |
| pipeline 只比一律时间表好不到 1pp | 学习型类型之间的偏好差别太小，零样本选择的价值有限；下一轮要把非学习型类型或新的卡住方式加进动物园 |
| 只用 R5-PCA2 的 pipeline 明显差于机制特征 | 以往跨类型失败的主因是指纹，换成机制特征即可修复 |

# 九、执行顺序

1. 完整性审计（开始，含并行任务目录清单与 `squeue`）→ 复现门 → 新类型实现、坐标系测试与单元测试 → 强化学习训练环境的等价性测试 → 开工记录与收据（菜单、state 划分、规模上限、起始特征、锁定类型清单）。
2. 新类型训练（GPU；锁定类型也可以在此时训练，但训练曲线以外的结果不看）。
3. 开发类型：能力门 → 标签与探测（复用优先）→ pipeline 开发与留一类型检验（迭代）→ 规模曲线。
4. 冻结最终 pipeline。
5. 锁定类型：能力门 → 探测 → pipeline 选臂并留收据 → 标签 → 锁定终点。
6. 完整性审计（结束）→ 交付。

任何阶段被挡住时，把受影响的类型记为缺口并写明原因，继续其余部分。只有源码保护、DB 规则或复现门对全部类型都无法满足时才整体停下。
