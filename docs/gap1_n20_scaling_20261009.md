# Gap1 scaling replacement: N=2, 10, 20

On 2026-10-09 the requested scaling endpoint changed from N=50 to N=20.
N=50 eta work was cancelled before its first seed finished. The accepted
N=50 frozen Flow and its earlier opposing evidence remain archived, but no
further N=50 eta rollout is planned. N=2 and N=10 frozen controllers are
unchanged.

N=20 has no pre-existing checkpoint or demonstration dataset. Its Flow will be
trained from scratch; no N=50 or N=10 weights will be resized or transferred.
The physical plant, robot radius, dynamics, 0.62 m Gap1 opening, accepted
hard safety projection, and later OrthoFlow3 eta semantics remain unchanged.
The N=20 horizon is 16,000 steps, matching the established `800*N` scaling.

The first N=20 data collection (`n20_competence_data_v1`) was stopped before
dataset finalization when an old `solo` selector was found to select a suffix
of the left-agent array rather than one agent. Its preflight and partial log
are retained as an aborted audit. The selector is fixed to a length-one
indexed array and verified for all 20 case indices. A new, outcome-blind
`n20_competence_data_v2` collection has been submitted as Slurm job 9620.
It requests 48 independent TRAIN and 12 DEV physical seeds, five non-opposing
modes (`solo`, `five`, `half`, `parked_half`, `full`), two row permutations, and
paired x-reflected trajectories. Each accepted pair contributes equal L→R
and R→L trajectories and transitions. Every demonstration must terminate
with all 20 agents at their goals; gate crossing alone is insufficient.
The generator performs the shared rollout-cache preflight first.

The from-scratch N=20 set-attention Flow training job 9647 depends on job
9620 succeeding. Its 20,000-step schedule uses active-agent normalization,
early-state and near-goal sampling, and balanced direction data. It does not
contain opposing traffic or priority demonstrations. Checkpoint choice will
use only DEV non-opposing controls. Fresh non-conflicting acceptance and the
original opposing test remain closed until a candidate is selected, then the
checkpoint is frozen before opposing evaluation.

CPU projection timing on the same initial-state snapshot, with the unchanged
hard projection applied twice per step, was 5.8 ms at N=20 versus 26.6 ms
at N=50 (50 repeated calls each). This is a timing probe, not an end-to-end
rollout benchmark. Together with the 16,000 versus 40,000 step horizons, it
suggests N=20 labeling can be roughly an order of magnitude faster than N=50;
the conservative end-to-end estimate is 2–4 days including new Flow data,
training, validation, opposing audit, and exact Q16 labels. The latest
resource instruction gives another Slurm task priority for twelve of the 24
CPU slots whenever it is running or waiting for resources. When no other task
is active, our jobs may use all 24 slots. The user-level
`gap1-cpu-priority.service` runs
`diagnostics/gap_flow_scale_20261007/n20_cpu_priority_governor.py` every five
seconds: it detects jobs outside the registered Gap1 job IDs, changes the
N=2/N=10 eta-array throttles, and cancels excess resumable eta tasks if the
other task needs to start. Every cancellation is journaled for exact-index
recovery. New Gap1 Slurm IDs must be registered in the governor and its
service restarted before their submission. The N=20 collection, audit, and
held training jobs are already registered. This dynamic policy supersedes
both the static twelve-slot reservation and the earlier 2026-10-10 09:00
reduction to nineteen. N=10 array task 185 was canceled while initially
freeing twelve slots and queued as dependent recovery job 10024; its partial
atomic per-seed results remain reusable.

The outcome-blind N=20 evaluation schedule is fixed before training finishes:
DEV checkpoint selection uses four fresh physical states per non-opposing mode
with master seed 162020; pre-freeze acceptance uses twelve different DEV
states per mode with master seed 398201. The eight modes are single-even,
single-odd, few-even, few-odd, full one-way in both directions, and temporal
release with either side first. The original opposing task is reserved for
TEST split, master seed 2026102012, twelve independent states, and opens
only after the selected checkpoint is frozen. Seed/physical-state overlap
with training demonstrations and the later eta split was checked from the
predeclared RNG policies: all pairwise seed intersections are empty. Physical
state hashes will be checked again once both datasets are materialized.

Candidate snapshots are ranked on the selection set by (1) zero collision
and numerical failures, (2) the worst per-mode complete-success count,
(3) total complete successes, (4) mean final goal occupancy, then (5)
smaller mean safety-projection correction. Offline validation loss is a
tie-breaker only. The separate twelve-case-per-mode acceptance set is opened
once for the selected candidate, not used to rank snapshots.
Each N=20 training snapshot may be screened in its raw sampling form and,
only if the paired DEV observation/action reflection audit is exact, with
the same N=20 weights under x-reflection-averaged sampling. This is a
predeclared Flow-only symmetry adapter, not a transferred N=50 model,
safety change, or opposing-traffic rule.

Pre-freeze acceptance requires at least 11/12 complete, collision-free
successes in each of the eight fresh categories, zero collisions and
zero numerical failures,
no severe directional asymmetry, and full-goal occupancy on successful
dense episodes. Gate crossing alone cannot pass. N=20 becomes READY_FOR_ETA
only if the frozen opposing evaluation also yields a meaningful,
collision-free coordination gridlock regime under the unchanged safety
projection.

The N=2/N=10 eta work already in progress remains useful. Its exact physical
state and eta identities will be reused in a new N=2/10/20 design via the
shared rollout cache after the N=20 prerequisite passes. No N=20 eta data
will be generated before frozen Flow competence and opposing gridlock are
established.

## New N=20 data and candidate training

The `n20_competence_data_v2` collection and independent phase audit closed
without teacher failures. TRAIN contains 480 complete demonstrations per
direction and 1,344,100 transitions per direction, paired exactly by
reflection. DEV contains 120 complete demonstrations and 327,770 transitions
per direction. The 48 TRAIN and 12 DEV physical seeds are disjoint. Every
trajectory ends with 20/20 goal occupancy, not merely a gate crossing. The
TRAIN active-action supervision fractions per direction are 43.60% approach,
3.30% entry, 7.66% crossing, 35.86% far post-gate, 8.47% near-goal, and
1.11% settled. See `n20_competence_data_v2/collection_report.json` and
`phase_audit.json` for exact counts and definitions.

The first training submission (job 9647) exited immediately because the
generic `train_flow.py` CLI omitted the already supported
`near_goal_distance` argument. The CLI now passes that argument unchanged to
the existing trainer; the N=20 request remains at 1.0 m. The same declared
training configuration was resubmitted as job 10459 with a 50 GB memory
reservation (matching the observed scale of earlier larger-N training). It
finished 20,000 updates from random initialization; the offline fixed DEV
loss is 0.058449 at the final snapshot. This is only an offline diagnostic,
not evidence of closed-loop competence. The ten raw snapshots are being
screened under the predeclared non-opposing DEV set in job 10491; opposing
TEST remains unopened.

The first competence screen rules out a simple offline-loss choice. The
step-20,000 raw checkpoint timed out in all eight single-active screen cases:
seven of eight agents crossed the gate, none completed the final 0.08 m goal
requirement, and there were no collisions. The remaining R→L agent stalled
against the gate-side wall before crossing. In two inspected post-gate
traces, the unchanged expert requested 0.5 m/s toward the final goal while
Flow's late goalward component was near zero or negative; safety correction
was small at the endpoint. The step-6,000 checkpoint achieved only 3/32
complete successes across the eight selection modes, including 0/4 one-way
in either direction. A dense trace had 18 agents requesting motion at once
although the one-way teacher's release pipeline moved only a few at once.
This identifies gate-side navigation, terminal-convergence, and queue-onset
coverage problems under non-opposing traffic.

The paired DEV observation and expert action reflection checks had exactly
zero error. Reflected versions of steps 6,000 and 20,000 were screened on
the same eight single-active states: 3/8 and 2/8 successes, respectively,
so reflection alone does not fix competence. These are screening results,
not pre-freeze acceptance. No opposing TEST state has been opened.

The competence-only data continuation starts from TRAIN source trajectories.
A broad terminal perturbation collection produced exactly 384 successful
mirrored recoveries per direction, 85,333 transitions per direction, zero
geometry rejections and zero expert failures. Every recovery finished with
20/20 goals under the accepted safety projection. The
`n20_competence_merged_v3` manifest adds these to the untouched v2 data.
Separately, 32 train-only Flow traces from 16 paired full-traffic source
seeds supplied three early queue anchors each. Mirrored expert continuations
from those anchors are being generated in four shards before a v4 merge.
The continuation trainer keeps the existing architecture and fixed phase
sampler; its initial N=20 checkpoint will be chosen only after the complete
non-opposing raw snapshot screen closes.

The resource governor now holds a resumable eta array if no slot remains,
then releases it when the priority task or N=20 fixed jobs finish. Earlier
array throttling alone repeatedly canceled N=2 Q16 workers because one
worker was restarted after every cancellation; this was detected from the
preemption journal and fixed before further repetitions. Already committed
per-seed results are intact, and canceled indices remain recoverable under
their original physical-state/eta IDs.

The onset collection subsequently closed with 96/96 successful recoveries
per direction and 548,574 transitions per direction; all four shards had
zero teacher failures. The wall-adjacent single-agent collection also closed
with 96/96 successful mirrored recoveries per direction, 19,627 transitions
per direction, and zero teacher failures. The final `n20_competence_merged_v5`
contains 1,056 TRAIN trajectories and 1,997,634 transitions **per direction**.
The original 120 DEV trajectories and 327,770 transitions per direction are
unchanged. All 2,112 TRAIN trajectories finish with 20/20 goals; the phase
and provenance audit passed. No opposing-flow demonstration or N=2/N=10
checkpoint enters this N=20 dataset. A single N=20 continuation trainer is
prepared with 20% early-nominal, 20% near-goal, 20% queue-onset, 15% terminal,
and 15% gate-local sampling. It has not been launched pending the completed
raw non-opposing checkpoint ranking.

The complete raw screen subsequently closed: all ten snapshots had zero
collisions and numerical failures, but the best (step 18,000) achieved only
4/32 complete DEV successes, with worst-mode success 0/4. Its selection
report is `n20_raw_checkpoint_selection.json`; this non-opposing choice,
SHA256 `08bcb18fadf4eab93f6379f9ef02516eb5b620d286538435246c456ec0f0a368`,
initialized one v5 continuation. The v5 dataset has exactly 1,056 TRAIN
trajectories and 1,997,634 transitions per direction, including paired
queue-onset, gate-local, and terminal recoveries. DEV is untouched.

The first v5 snapshots did not pass the complete-task screen: step 1,000
achieved 6/32 and step 2,000 achieved 0/32 on the predeclared non-opposing
DEV controls, with zero collisions. A step-2,000 single-active agent crossed
the gate but stopped about 0.60 m from its goal; its last 2,000 Flow commands
had essentially zero mean goalward component. In a five-active step-1,000
case, a previously settled agent was slowly displaced outside the 0.08 m
goal tolerance by the accepted safety projection, then Flow failed to restore
it. The `--goal-stop` evaluator zeros reference actions while inside the
tolerance; this trace therefore tests **recovery after displacement**, not
whether Flow directly moves a settled agent. These are competence failures,
not opposing-flow deadlocks.

The v5 sampler gave 20% early, 20% near-goal, 20% queue-onset, 15% terminal,
15% gate-local, and only 10% ordinary joint-state sampling. This likely
underweights far post-gate travel in a dataset where completing all final
goals is the actual task. A second, controlled v6 candidate keeps the same
N=20 architecture, paired dataset, raw-selected initialization, and unchanged
safety chain. It assigns 25% to TRAIN states with an actually moving agent
past the wall and more than 1 m from its goal, 20% ordinary sampling, and
smaller bounded fractions to the other phases. It also adds weight 1 to the
already implemented ten-step Flow endpoint action loss, with a moving-agent
factor of 4, to supervise the **executed Flow endpoint** near the final goal.
The post-gate selector finds 2,408,654 eligible TRAIN joint transitions; its
condition is x-reflection symmetric. V6 training completed in job 11354;
the config records `test_opened=false`. Its first closed-loop pilot covers
fresh non-opposing single-active DEV cases at four snapshots. Neither v5 nor
v6 is frozen or has opened opposing TEST.

The v6 early gate also failed. Four snapshots (steps 1,000, 3,000, 5,000,
8,000) each ran the same eight fresh single-active DEV cases; complete
success was respectively 2/8, 3/8, 0/8, and 3/8. In the step-3,000 failures,
four of five inspected agents crossed the wall, but late Flow goalward
commands were near zero and safety correction was tiny. Endpoint supervision
and on-policy post-gate sampling alone therefore did not provide reliable
off-policy terminal recovery. These pilot results reject v6 without spending
full dense-screen budget. The full v5 snapshot screen continues for a fair
closed-loop ranking.

To address the measured off-policy deficit, a new TRAIN-only collection
starts from v5 step-1,000 non-opposing model traces on independent source
cases 16–19 of `solo`, `five`, and `full`, in both directions. The accepted
Flow→bound→hard-projection chain and goal-stop evaluator produce the traces;
the existing same-direction expert supplies only recovery demonstrations.
No opposing-flow state or priority negotiation is included. Fixed absolute
anchors (3,000/5,000/7,000/9,000) missed a short real post-gate interval in
the first four solo-LR traces. A symmetric filter now identifies times when
an initially moving agent is on its goal side of the wall yet more than 1 m
from goal, and takes the 20/50/80% positions within that interval. It logs
all rejected anchors. The first shard produced 9/9 successful mirrored
expert recoveries per direction, 936 transitions per direction, with zero
teacher failures; solo-RL produced 19/19 and 1,323 transitions per direction.
Remaining categories are in progress. Three simultaneous GPU model-trace
workers failed before producing usable traces due shard memory exhaustion;
those categories were rerun on the CPU partition under the same source and
checkpoint, retaining the failure logs. N=20 remains unfrozen.

The full post-gate collection closed with 125 successful mirrored recoveries
and 158,413 transitions **per direction** across solo/five/full TRAIN source
categories. The two unsuccessful full-RL expert continuations are retained in
the collection report and excluded as failed demonstrations; every accepted
sample is added as an LR/RL pair. `n20_competence_merged_v7/dataset` was merged
from the unchanged v5 source and passed the independent phase audit. Its TRAIN
split has 1,181 trajectories and 2,156,047 transitions per direction from
the same 48 physical source seeds; DEV remains 120 trajectories and 327,770
transitions per direction from 12 disjoint seeds. The complete v5 screen chose
step 1,000 by 6/32 full DEV successes, with zero collisions but worst-mode
0/4; no v5 checkpoint passed competence. Where a checkpoint step lacks an
exact logged offline DEV loss, the selector linearly interpolates neighboring
logged losses for the final tie-breaker only. The winner was separated on
closed-loop success, so interpolation did not affect its selection.

One v7 continuation from that selected v5 checkpoint reallocated supervision
to 20% model-derived late post-gate recovery, 10% general far post-gate

goal/gate/queue categories. It retained the N=20 set-attention architecture,

On the predeclared eight-case single-active DEV pilot, v7 snapshots at 1k,

The complete v7 raw Flow screen closed with zero collisions/numerical errors,

One controlled v8 continuation uses the same v7 data, architecture,

The parallel, lower-priority N=20 work is capped dynamically. While the
independent controller-Q task is queued or running, 12 of the 24 CPU slots
remain reserved for it and all of our running N=20 jobs together use at most
12. If it is absent, the governor may release resumable N=2/N=10 eta workers
to occupy idle slots. The governor records any exact eta task cancelled to
make room for priority work; those task indices require exact recovery before
their respective eta dataset is declared complete. The scheduling policy does
not change rollout seeds, labels, or checkpoint selection.

The early v8 screen at steps 1k and 2k had only 2/8 single-active successes
and 0/8 one-way successes at each step, despite zero recorded collisions.
Later snapshots remain in the pre-freeze screen; these early results alone do
not establish a final v8 verdict. Because a new endpoint objective can trade
waiting against basic movement, a separate v9 **loss-only** continuation was
started from the same DEV-selected v7 step-3k weights. It keeps the same
balanced v7 data, architecture, sampler, single-sample deployment, and
safety projector, but changes active-motion loss weight from 20 to 10, the
weight used by the accepted N=10 controller. This tests whether the unusually
large active-motion weight contributed to false release commands. All eight
v9 training snapshots have been produced; the fixed offline DEV loss at step
8k is 0.0561, which is not evidence of closed-loop competence. A separate
same-seed non-opposing DEV screen of single-active and one-way traffic in both
directions is running before any fresh acceptance or opposing test. No N=20
controller has been frozen and no N=20 eta generation has begun.

A further predeclared transfer control is queued **after** the v9 pilot array,
so it cannot displace the priority task or the currently allotted N=20
screening CPUs. The accepted frozen N=10 model has the same set-attention
parameter shapes and eight-feature observation/two-dimensional action
semantics; it is a useful test of whether N=20's remaining error comes from
optimization from scratch rather than a missing feature. Candidate v10 copies
only those frozen weights into a newly fitted N=20 Flow, then trains on the
same balanced non-opposing v7 demonstrations and phase sampler. It uses the
N=10 action-scale convention and CFM motion weight 10. Thus transfer and
action scaling are a package-level ablation, not separately identified causal
factors. The N=10 checkpoint is never edited. V10 will not be chosen using
opposing traffic, and its queued launch will be canceled if an earlier
candidate passes fresh non-opposing acceptance.
Its first closed-loop screen is queued only after a successful v10 training
job: two paired DEV cases in each of four core modes at all ten 2k snapshots.
This 8-case-per-snapshot pass is a pilot for checkpoint selection, not the
fresh 12-case-per-mode acceptance gate. Any promising snapshot must complete
the fuller non-opposing control suite before it can be frozen.
