# 零、本轮要做什么（用户 2026-10-18 确定）

**pipeline 的动作就是一个时间表：** 前期一个 η、后期一个 η，在切换时刻换过去。数据表里另外报告一个不带时间表的 pipeline（整局只用一个 η）作对照。

**理想的形态（用户确定）：** 时间表的三样东西全部由 pipeline 学出来：
1. 前期 η 是学出来的；
2. 后期 η 是学出来的；
3. 切换时刻是学出来的。实在学不出来，切换时刻才退回固定的第 500 步。

**本轮要回答的问题：** 这三样能不能都由 pipeline 自己学出来（生成器提议、critic 挑选），而不是由人写死成"前 500 步 η13、之后 η10"或"按进度从 η13 切到 η10"？

**为什么必须回答这个问题：** 到目前为止，时间表"前期 η13、后期 η10"是人定的：
- η10 与 η13 都是 Ring 研究中一个固定的 16 个 η 的候选库里的元素（编号 10 与 13）；
- η10 之所以被用作"后期 η"，是因为在最初 14 个环形交换场景流匹配策略中，有 9 个的最佳固定 η 是 η10，它成了旧的默认值；
- "先 η13、后 η10"是 round9 在 4 个流匹配策略上做切换实验时发现的；
- 跨type1b 的 pipeline 虽然用了生成器，但后期 η 仍写死为 η10，锚点也写死了 η13 → η10。

这样论文就必须解释"为什么后期是 η10"，而唯一的答案是"在流匹配策略上手工试出来的"，这和"对黑盒 controller 零样本"的定位矛盾。另一方面，round22（`diagnostics/ring_eta_pair_generality_v1`）已经表明 (η13, η10) 不是唯一有效的一对：
- η7 → η4 的时间表收益 +43.3pp [22.3, 63.1]，η11 → η6 为 +37.4pp [22.3, 51.8]；
- 而 [5, 9]、[3, 8] 这样两端都失败或效应很小的 η 对没有收益。

所以只要两个 η 各自在不同阶段有优势，时间表就有效。这说明让 pipeline 自己挑一对是可行的。

# 四、动作与候选

**提议集：** 每个 state 用冻结的生成器给出 8 个 η 提议：变换后的均值与 7 个随机样本，随机样本的确定性种子沿用跨type1b 的派生规则（前 4 个样本必须与跨type1b `CANDIDATES.json` 中同一 state 的提议逐位一致，后 3 个按同一规则继续派生）。生成器不看 controller。

**动作：** a = (η_前期, η_后期, 切换时刻)，η_前期与 η_后期都取自该 state 的 8 个提议。
- **自学时间表的 pipeline（主方法）：** 候选为 64 个有序对 × 切换时刻 ∈ {200, 300, 400, 500, 600}，前期 η、后期 η 与切换时刻由 critic 一并选择。其中对角元（η_前期 = η_后期）就是"整局固定一个 η"，与切换时刻无关。
- **固定第 500 步切换的 pipeline（退路）：** 候选为 8 × 8 = 64 个有序对，切换时刻固定为第 500 步。只有当主方法在开发中学不出切换时刻（见第七节）时，它才作为本轮冻结的主方法；无论如何都要报告。
- **不带时间表的 pipeline（对照）：** 只在 8 个对角元中选。

**时间表生成器（开发中可选的第二步）：** 冻结的生成器只学过"整局固定一个 η"的成功集，提议集中在 (0.87, 0.10, 0.05) 附近，很少提出像 η10 那样的 η。若开发前报告或留一类型检验显示提议集是瓶颈，允许训练一个**时间表生成器** q(η_前期, η_后期, 切换时刻 | h)：
- 结构沿用冻结生成器的对角压缩高斯（η 盒相同），输出维度扩为 3 + 3 + 1（切换时刻按 [200, 600] 做同样的 tanh 压缩），可以用冻结生成器的权重初始化前期 η 的部分；
- 训练目标与原生成器相同：在源类型的训练 state 上，以成功的动作为正例的负对数似然，加 0.25 的同 state 正负例排序项；
- 只用源类型的标签（每折单独训练，嵌套选 checkpoint），η13、η10 及其标签不得进入；
- 它给出的提议与冻结生成器的 8 个提议合并成候选，再由 critic 挑选；新提议的标签按第五节同样的抽样规则补跑，计入追加预算；
- 是否启用、启用后的效果，都写进迭代日志，并在 AXIS_TABLE 中单列"冻结生成器提议"与"冻结生成器 + 时间表生成器提议"两种 pipeline。

**η13 与 η10 不得进入任何候选，也不得作为后期 η 的默认值。** 前 500 步 η13、之后 η10 的时间表与按进度切换时间表只作为对照方法出现，它们的标签不得用于训练 critic。

开发中可以改变提议数或切换时刻集合，但必须写进迭代日志，不得加入 η13、η10 或从它们派生的 η。

# 七、开发与冻结

**开发前先报告（只用训练 state 的标签）：**
- 对角元（整局固定 η）中事后最佳 − 非对角对中事后最佳，按类型列出：两 η 的时间表在提议集中是否真的比单一 η 好；
- 非对角对中，"在不同阶段各有所长"的对（η_前期 整局固定时前期进度好、η_后期 整局固定时后期不失败）所占的比例；
- 提议集到 η13、η10 的距离分布。

**留一类型开发检验（DEVELOPMENT，9 折）：** 每折留出一个类型，其余 8 个类型为源；全部预处理、超参数与 checkpoint 只能用源类型内部（嵌套）来选。由于训练 state 上只标出了部分候选，留出类型的打分只在已标出的动作上做：报告 critic 选中的已标出动作的成功率，以及 critic 对已标出动作的排序准确率。类型等权合并为主，另报 controller 等权。

**开发目标（达到就冻结；达不到也要在预算内冻结当前最好的版本，并如实报告）：**
- 留出类型上，critic 在已标出动作中的排序准确率不低于跨type1b 在 13 个候选上的水平；
- 留出类型上，critic 选中的已标出动作的成功率不低于对照 1 在同一批 state 上的成功率减 1pp。

**切换时刻是否学得出来（决定主方法，开工时写定规则）：** 在留一类型检验中，比较自学时间表与固定第 500 步切换两种 pipeline 在留出类型上的成功率（只在已标出动作上），以及 critic 对"同一有序对、不同切换时刻"的排序准确率。若自学时间表的类型等权成功率不低于固定第 500 步切换减 0.5pp，且这一排序准确率高于 0.5（随机水平），就冻结自学时间表为主方法；否则冻结固定第 500 步切换为主方法，并在报告中写明"切换时刻没有学出来"及证据。两种都冻结并在新评估 state 上评估，主终点按冻结前选定的那一种判定。

**冻结：** 把 9 个留一类型模型与用全部 9 个类型训练的最终模型，连同代码、输入定义、提议规则、选择规则写入 `FROZEN_PIPELINE.json` 并留 UTC 与 sha256 收据。然后为 24 个新评估 state 计算提议并用冻结模型选择（每个 controller 用没见过其类型的留一模型），留选择收据。选择收据的时间必须早于新评估 state 的第一个 rollout 提交。

# 八、新评估 state 上的一次性评估（CONFIRMATORY）

| 编号 | 检验内容 | 判定标准 |
|---|---|---|
| 终点 1（主） | 学出来的时间表能否替代人定的时间表 | 类型等权：冻结的主方法 − max(对照 1, 对照 2) 的配对 CI 下界 > −1pp（非劣）；另报 CI 下界是否 > 0（优于），以及相对对照 1、对照 2 各自的差 |
| 终点 2 | 切换时刻是否学出来了 | 自学时间表的 pipeline − 固定第 500 步切换的 pipeline 的配对差与 CI；自学时间表选中的切换时刻分布（若全部落在第 500 步，就说明没有学出来） |
| 终点 3 | pipeline 是否真的用上了时间表 | 冻结的主方法 − 对照 4（不带时间表的 pipeline）的配对 CI 下界 > 0；并报告选中非对角对的比例 |
| 终点 4 | 相对跨type1b 的进步或代价 | 冻结的主方法 − 对照 3 的配对差与 CI：去掉写死的 η13、η10 之后，成功率损失了多少，或者没有损失 |
| 终点 5（描述性） | pipeline 选出的两个 η 是什么 | 选中的 η_前期 与 η_后期 的分布（三个分量的散点图与直方图，按类型着色）；它们到 η13、η10 的距离；η_后期 − η_前期 的方向与 η10 − η13 的方向的夹角余弦；按类型列出选中的切换时刻分布 |

另报：用全部 9 个类型训练的最终模型在新评估 state 上的结果（各类型都见过，只作参照）；不看 controller 的 critic 的结果。

**CI：** 按共同协议第四节，5000 次配对 bootstrap；类型等权时先在类型层重抽，再在 controller 层，再在 state 层成簇重抽（两个 seed 保留在同簇）。unknown 按下界计，另报上界。

# 九、执行顺序

1. 完整性审计（开始，含并行任务目录清单与 `squeue`）→ 复现门：跨type1b 的 16 条记录逐位一致；冻结生成器在跨type1b 的 state 上重算的前 5 个提议与 `CANDIDATES.json` 逐位一致。不一致就停下报告。
2. 为 48 个训练 state 与 24 个新评估 state 计算 h、c 与 8 个提议；按种子抽出训练标签用的动作；冻结清单并留收据。
3. **试点：** 先在 3 个类型（环形交换场景流匹配策略、扩散行为克隆策略、参数共享独立近端策略优化强化学习策略）上跑训练 state 的标签，报告第七节"开发前先报告"的三项。试点结果不改变后续设定，只写进迭代日志；之后补齐其余类型。
4. critic 开发与留一类型检验（迭代）→ 冻结。
5. 新评估 state：冻结模型选择并留收据 → 标签 → 终点 1–5。
6. 完整性审计（结束）→ 交付。

任何阶段被挡住时，把受影响的类型记为缺口并写明原因，继续其余部分。只有源码保护、DB 规则或复现门无法满足时才整体停下。

# 十、结论映射

| 观察结果 | 结论 |
|---|---|
| 终点 1 与终点 3 都通过，且主方法为自学时间表 | 理想形态成立：前期 η、后期 η 与切换时刻都由 pipeline 学出来，不需要人定 η13、η10 与第 500 步；论文中时间表的设计不再依赖手工发现 |
| 终点 1 与终点 3 都通过，但主方法退回固定第 500 步切换 | 两个 η 学出来了，切换时刻没有；论文写"η 由 pipeline 学出，切换时刻固定"，并报告切换时刻没学出来的证据 |
| 启用时间表生成器后才通过 | 冻结的生成器不足以服务时间表，需要专门为时间表学习的生成器；它成为 pipeline 的标准部件 |
| 终点 5 显示选中的两 η 接近 η13、η10，或方向与 η10 − η13 一致 | pipeline 自己重新发现了"前期偏一种修正、后期偏另一种修正"的结构；可以据此解释 η10 的角色，而不需要把它写死 |
| 终点 1 通过，但选中的两 η 与 η13、η10 差别很大 | 有效的 η 对不唯一（与 round22 一致），pipeline 找到了另一对 |
| 终点 1 不通过，开发前报告显示提议集中没有好的非对角对 | 冻结的生成器只学过整局固定 η 的成功集，提不出好的后期 η；下一步需要能为"后期"提议的生成器，例如在切换时刻用当前 state 重新查询生成器 |
| 终点 1 不通过，但提议集中有好的对 | 瓶颈在 critic 对 η 对的排序；看三种比较下的排序准确率 |
| 终点 2 显示自学时间表优于固定第 500 步切换 | 切换时刻也可以由 pipeline 自己学，按进度切换规则中的 p* 也不必人定 |
