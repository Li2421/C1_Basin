# 一、要回答的问题：分布式执行下，结论是否仍然成立？

到目前为止，整条管线都是集中式的：
- 联合策略：MACFlow，p(u₁…u_N | x)；
- 安全投影：对所有机器人联合求解；
- η：全队共享；
- B_rel：使用所有机器人的位置。

而经典的多机器人死锁（Grover 等人分析的力平衡死锁）主要出现在分散式 CBF 安全过滤器中。仓库里的集中式专家规划器在 Ring 的 nominal 初态上可以 210/210 全部成功，所以“集中式条件下的死锁解决”这一定位很弱。

我们方法中的核心部分本身不需要集中式：
- 时间表只按时间切换，每个机器人用自己的时钟即可；
- B_goal 与 B_perp 只用到机器人自身的信息，B_rel 可以只用感知到的邻居；
- 探测与 critic 的选择在部署前完成。

round27 显示，时间表的大收益只出现在 Flow 类 controller 上（MPC、势场类没有）。因此本轮使用 Flow controller。

**本轮问题：** 把安全投影、修正与时间表都改为每个机器人在本地计算，即分散式安全层：
1. 死锁或失败会不会更多？
2. 时间表相对固定 η 的优势是否仍然存在？
3. 结论是否仍然不依赖 controller？
4. 与经典的分散式死锁处理基线相比如何？

# 二、两条新的执行管线（只在本轮目录中实现，不改已有代码）

两条管线都采用 TT 位置（nominal → 安全投影 → 加修正 → 再投影），与 round27 中 Flow TT 参照的结构相同，只把安全层与修正改为分散式。

**D-shared（主管线）：**
- **策略推断：** 仍使用 joint MACFlow，假设观测通过通信共享。每个机器人计算联合网络的输出，只执行自己那一行。在预注册中写明这一通信假设。
- **安全投影：** 每个机器人只解自己的 CBF QP。
  - 约束集合：与每个邻居的成对避碰约束（标准的分散式 CBF 做法：成对约束各承担一半，邻居的动作按其 nominal 或零速度假设，预注册写明二选一），以及与障碍、外环的约束（由自己完全承担）。
  - 约束形式与参数尽量沿用集中式版本，例如 class-K 系数与安全裕量。
- **修正：** 每个机器人只用自身信息计算 B_goal_i 与 B_perp_i（后者用自己投影后的安全动作），B_rel_i 用全部邻居。
- **时间表：** 每个机器人在第 t 步自行切换 η，不需要通信。

**D-local（敏感性管线）：** 与 D-shared 相同，但安全约束与 B_rel_i 只计入感知半径 r_sense = 1.5 m 以内的邻居。

**集中式对照：** 同样的 controller 和 state，使用 round27 Flow TT 参照的集中式 TT 实现。

**一致性门：**
- 当 r_sense = ∞，且分散式 QP 退化为单个机器人时，确认各部件与集中式实现在数值上一致。若不可能逐位一致，要说明原因并报告误差。
- 用 round27 的方法复现 16 例集中式 TT 记录。

**精度：** 全部导入完成之后，显式恢复协议规定的精度（round25 的教训），并记录 x64 状态。

# 四、设计（执行前写好 PREREGISTRATION.md，附 UTC 时间与 sha256 收据）

**controller：** round10 的 14 个原 Ring Flow（best.pkl），覆盖全部 14 个配方。

**state：** 32 个全新 state，与 DB 中所有 state 去重。pilot 与评估使用不重叠的种子区间（round27 的教训：事先算好区间，并在预注册中写明）。

**臂（D-shared、D-local、集中式 TT 三条管线都跑）：** F10、F13、S300、S500，seed 0–1。

**基线（只在 D-shared 安全层上运行）：** B-RHR、B-RHR + F10，seed 0–1。

**专家：** 每个 state 规划 1 次。

**规模：** 14 × 32 × (4 × 3 + 2) × 2 ≈ 12,544 条，另加专家与一致性门。

**流程：** 按 shared_rollout_db 流程执行：design → preflight → 只跑缺失 → journal → 单进程 merge → postflight。新管线登记为新的执行身份。

**额外记录：**
- 每条 rollout 的碰撞情况：沿用连续运动的 swept clearance 检查，分散式安全层可能出现集中式时不会出现的违约；
- 数值失败；
- 停滞诊断：速度接近 0 超过 2 秒且未到达目标的机器人数与持续时间。Ring 没有正式的死锁判据，这一项只作描述，不得称为 deadlock。

# 五、预注册的终点与判定

所有 CI 先在 controller 层重抽，再在 state 层成簇重抽，共 5000 次。unknown 按下界计，另报上界。

| 编号 | 检验内容 | 判定标准 |
|---|---|---|
| DC1（主） | 时间表优势在分散式下是否仍在 | 在 D-shared 中，“最佳时间表 − 最佳固定 η”的平均值 CI 下界 > 0，且 ≥ 70% 的 controller 满足 S(最佳) ≥ max(F10, F13) − 1pp |
| DC2 | 是否仍不依赖 controller | 在 D-shared 中，一律用 S500 的平均遗憾 ≤ 3pp（相对 4 个臂的 oracle），并与“每个 controller 的最佳固定 η”比较 |
| DC3 | 分散化的代价 | 对每个臂比较 D-shared 与集中式 TT 的成功率差，并报告碰撞、数值失败、停滞诊断（描述性） |
| DC4 | 与经典基线对比 | 在 D-shared 中，S500 的成功率高于 B-RHR 与 B-RHR + F10，配对 CI 下界 > 0 |
| DC5 | 感知受限（描述性） | D-local 相对 D-shared 的变化 |

另外报告集中式专家的成功率与规划耗时，作为上界参照。

# 六、结论映射

| 观察结果 | 结论 |
|---|---|
| DC1、DC2、DC4 都通过 | 时间表的优势和“不依赖 controller”的性质，在分散式安全层下仍然成立，并优于经典的分散式死锁处理。论文中的集中式问题降级为“策略推断需要共享观测”这一有限假设 |
| DC1 通过，DC4 不通过 | 时间表仍有效，但不如简单的右手规则。论文需要重新审视方法的定位 |

| 出现任何碰撞 | 先报告安全问题，所有成功率结论都附上这一前提 |
