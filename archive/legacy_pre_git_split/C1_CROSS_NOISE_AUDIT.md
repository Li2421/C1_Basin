## 方法及结果

每个 checkpoint 有 64 个起点，各两个固定噪声。用噪声 A 的完整轨迹风险预测噪声 B 的死锁，反向也计入；bootstrap 按起点聚类，保留两个噪声一起重采样。same-rollout AUC 是语义一致性，cross-noise AUC 才提供有限的跨实现信息。两者都不是已经通过的起点预测实验。

当前 ordered 候选结果：

| 更新 | 死锁/128 | 风险为零的比例 | 同轨迹 AUC | 跨噪声 AUC |
|---|---:|---:|---:|---:|
| 0 | 5 | 95.31% | 1.000 | 0.682 |
| 4 | 4 | 89.84% | 1.000 | 0.448 |
| 8 | 2 | 98.44% | 1.000 | 0.492 |
| 12 | 7 | 76.56% | 1.000 | 0.606 |
| 16 | 14 | 81.25% | 1.000 | 0.899 |

第 8 次更新中，两个发生死锁的起点在另一噪声下均不死锁；126/128 个评分为零。当前候选对这些罕见事件没有显示出跨噪声区分能力。第 16 次更新虽然跨噪声排序更好，但死锁反而更多，因此不能用 AUC 增加代表控制改善。

不确定性：起点和 checkpoint 都是已经看过的开发数据；每个起点仅两个噪声；少数事件下非参数 bootstrap 无法创造未观察到的事件结构，其区间可能过窄。JSON 中保存的区间仅作描述，不能用作确认性显著性结论。评分使用整段 rollout，不是只看早期轨迹，也没有证明噪声是部署扰动的完整模型。

## 优化退化线索，不是因果结论

当前 16 个训练 batch 中有 6 个前向风险恰为零，其梯度范数中位数为 0.00743；10 个正风险 batch 为 358.95。零风险 batch 的 J_def 单步后/前比值中位数为 0.742，约下降 26%。旧 exact 训练相同比值约为 0.698。Adam 的归一化及重启动量可能放大低风险批次的回归 Safety 效应，但不同 batch 和 checkpoint 的这些汇总不能证明该机制导致验证退化。

零风险平台意味着该噪声实现不再提供风险梯度，即使同一起点在其他噪声下会死锁。需要同时审视 Monte Carlo 风险估计方差和优化步长，不能仅把问题归咎于优化器，也不能仅靠给风险添加指数放大解决。

## 下一阶段固定方向（尚未运行）

1. 起点评分与结局评测使用独立噪声；冻结策略和评分预算后，检查评分与多次闭环死锁频率的关联。完整预测 rollout 与短窗口预测分别报告，不能默认 20 秒够用。任务成功、普通 timeout、安全违规分开。
2. 同一策略的多个预测噪声用于估计 E[R|x0]，不是生成多条候选路径再选一个。检查多噪声平均相对单噪声评分是否减少零风险漏报，以及方差与计算成本。保留原 C1 的均匀起点分布，不添加困难样本补丁。
3. 早期动作干预使用同幅度负梯度、正梯度、随机方向及不干预对照；在预定早期时段后恢复原策略，以分离早期决策作用与后续持续救援。梯度可以考虑完整未来，但执行干预窗口必须固定。
4. 共享策略优化器对照保持初始化、风险、噪声、batch、双变量流程和预算相同；先验证是否真实改善风险与任务完成，再进入完整多种子训练。当前日志不足以选择 SGD 并宣称修复。
5. 预留独立 test 不用于上述开发；最终配置冻结后才用于确认性配对结果。扩展场景、多训练种子和安全审计仍是目标的必要条件，均未由本审计完成。

## 早期干预接口准备

新增 `single_integrator/c1/early_intervention.py`：调用原 `evaluate_deadlock_union.execute`，只在前 K 次 `field.prepare` 使用干预参数，之后在当前状态和原噪声下恢复参考参数。不是回到原参考轨迹的状态，也不是重放参考动作；因此保留早期动作造成的后续状态影响。K=0 为参考策略，K=max_steps 为全程干预。每次 replay 新建计数器，终止、两个硬投影、安全检查均由原执行器负责，没有改动其源码。

该接口只用于因果诊断，不进入训练或部署策略，不是针对场景的分时退让规则。输出标记 diagnostic_only；原 timeout 再分类仍由调用方完成。

CPU 标准库 unittest 检查通过：窗口边界、当前输入和投影函数透传、非法窗口拒绝、独立 replay 计数不泄漏。命令：`.venv-c1/bin/python -m unittest single_integrator.tests.test_c1_early_intervention -v`。这些是接口检查，未运行物理 rollout；真实 K=0/full-window 等价性与早期干预效果仍须后续实验验证。环境未安装 pytest，未为此改动环境依赖。

### 后续物理边界检查已完成

`scripts/check_c1_prefix_physics.py` 在 Slurm cpu 分区申请 1 CPU/4GB/10分钟，无 GPU GRES，强制 JAX_PLATFORMS=cpu、CUDA_VISIBLE_DEVICES 为空。使用 train 的首个起点和固定新噪声 8241801，以 Safety 与已有 C1 checkpoint 分别作为参考/替代参数，未按结局挑样本。

`results/c1_prefix_physics_cpu_v1/complete.json` 确认四次完整原时域回放均完成（各850步），K=0 对原参考、K=max_steps 对原替代策略的所有 trace 字段最大绝对差均为零，summary 除附加诊断字段外一致；原安全审计通过。保存全部四条 trace、源代码哈希、环境/CBF、checkpoint 哈希及固定种子。此次仅证明该起点上的边界一致性，没有证明早期干预有益，也不是泛化实验。原 summary 的 timeout 仍未在此检查中进行终末停滞细分，不能据此把其解释为普通 timeout。

四次回放用时约3.55秒（不含模型 setup），任务已退出、队列无本用户任务。CPU 上小规模前向规划诊断可能可行，后续无需因 GPU 暂停而完全停止物理验证；梯度训练的成本不能由此前向耗时推断。CPU/GPU 之间的数值轨迹等价性未验证，不能直接把 CPU 新结果与旧 GPU 结果合并；同一新实验应在固定 backend 上重新做配对。

### 可微 rollout 与物理执行器：不是完全数值等价

后续 `scripts/check_c1_early_forward.py` 检查的是另一层：新增可微早期干预 rollout 对原物理执行器。CPU、同一初始状态/噪声和已有非零残差参数下，K=0/100/850 的终止步数及 success/deadlock/timeout 一致，原执行器安全审计通过，但三者均未通过预设 atol=rtol=1e-7。完整测量 `results/c1_early_forward_cpu_v2/complete.json` 的 passed=false；没有放宽阈值改成通过。

K=0、100、850 的最大 applied 差分别为4.53e-7、4.08e-7、1.66e-6，最大位置差分别6.83e-8、3.45e-8、1.68e-7。原v1检查在第一个差异处断言失败，v2只改为收集所有窗口的差异，原阈值和失败结论不变。该检查不推翻前一个“同一物理执行器的wrapper边界一致性”结论，两者比较对象不同。

代码上实际环境 observation 是 float32；可微 observation 在float64状态上构造，Flow-BC内部转float32，但残差读取的输入精度存在差别。另有compiled scan与逐步执行的浮点运算差异。尚未通过消融归因，不能声称已经定位全部误差来源。此量级暂未在被测起点改变事件或动作尺度，Job35开发诊断保持冻结继续执行；结局仍以原物理执行器为准。不能据此宣称梯度无偏或在任意起点事件一致。
