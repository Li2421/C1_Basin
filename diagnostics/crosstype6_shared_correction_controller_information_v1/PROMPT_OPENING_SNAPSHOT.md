## 4.1 进度阈值学出

## 4.2 在线停滞触发

进度 p(t) 的定义与 `progress.py` 相同（4 个机器人到目标距离的归一化进度均值）。触发设置为 (W, ε)：从第 W 步起，若 p(t) − p(t − W) < ε，就在第 t 步触发。三个设置：

| 设置 | W（步） | ε |
|---|---|---|
| 敏感 | 25 | 0.010 |
| 中等 | 50 | 0.010 |
| 保守 | 100 | 0.005 |

触发前只加安全投影；触发后从前期 η 开始修正，此后按 θ 切到后期 η；若触发时进度已 ≥ θ，直接用后期 η。从不触发就整局不修正。触发设置也是动作的一部分（主方法中由 critic 按 state 选；"单一触发设置"消融中用源类型上嵌套选定的一个全局设置）。

**切换时重查（按第三节启用时）：** 后期 η 在实际切换的那一步，用冻结生成器按当时的状态重查。这一步是：平均进度第一次 ≥ θ 的那一步；或第 600 步兜底；或触发时进度已 ≥ θ 的那个触发步。重查放在与 controller 隔离的进程中执行，沿用跨type5 的实现（冻结生成器导入时会设置全进程 XLA 参数，从而改变 controller 的浮点计算顺序）。执行等价性测试另加一项：重查动作在切换前的轨迹前缀，与"整局前期 η"（有触发时为"同一触发设置下整局前期 η"）逐位一致，至少 8 条。

**执行等价性测试（开工时）：** 从不触发时，与只加安全投影的记录逐位一致（至少 8 条）；触发前的轨迹前缀与只加安全投影逐位一致（至少 8 条）；在线触发步与在保存轨迹上离线算出的触发步一致；θ = 0.968 且前期 η = η13、后期 η = η10、"不触发"时，与已有的人定双 η·按进度切换记录逐位一致（至少 8 条）。

**提前结束等价复用（沿用跨type4、跨type5 的规则与实现，复用标签不写共享 DB）：**
- 在同一 (controller, state, seed) 的只加安全投影保存轨迹上离线计算触发步；若在该局结束前从不触发，"在线停滞触发"动作的结果与只加安全投影相同，直接复用；

- 3 个"阈值"动作：η 对从第三节启用的来源中按种子抽，θ 从网格中均衡抽（不触发）；
- 6 个"触发"动作：三种触发设置各 2 个，η 对与 θ 按种子抽。
- 若按第三节启用了切换时重查：后期 η 的来源在"冻结提议"与"切换时重查"之间按种子分配。3 个阈值动作中 1 个用切换时重查，另 2 个用冻结提议对；每种触发设置的 2 个动作中 1 个用切换时重查。前期 η 一律取自该 state 的 8 个冻结提议。

η13、η10 构成的人定时间表标签不得进入训练。

# 六、模型、留一类型检验与冻结

- **critic：** 沿用跨type5 的结构、损失与训练规则（seed 17 / 23 / 41 集成，checkpoint、权重与预处理只用源类型内部的留一类型嵌套选择），动作分支按 4.4 扩展。训练两个版本：
  - **不看 controller 的 critic**：没有 controller 分支，用于第一层与在线停滞触发层；
  - **看离线探测特征的 critic**：controller 分支输入 4.3 的特征，并保留"完整分支与不看 controller 分支按概率加权"的结构，用于"离线探测特征"那一层。
- **选择：** 对每个 state 在候选中取集成均值最高者；各层只在本层允许的候选中选择（第一层没有触发设置；在线停滞触发层的候选全部带触发设置，另含"不触发"）。并列规则沿用跨type5。
- **留一类型检验（训练 state，19 折）：** 只在已标出动作上打分；报告选中动作的成功率、未评分比例，与排序准确率（另报"不同 θ 之间""不同触发设置之间"的排序准确率）。
- **冻结：** 19 个留一类型折与全部类型训练的最终版本写入 `FROZEN_PIPELINE.json` 并留 UTC 与 sha256 收据；新 state 上的全部选择在第一个新 state rollout 提交前密封。

# 七、新 state 上的开发检验

**state：** 24 个，按开工时写定的种子用 round10 生成器生成，与 DB 中全部 state 去重（包括跨type1b、跨type2、跨type1c、跨type3、跨type4、跨type5 的新评估 state），seed 0–1；冻结前不跑闭环 rollout。

**controller：** 19 个类型的**全部**合格实例（本轮要检查每个学习型类型是否 ≥ 90%，所以学习型也全部评估），每个 controller 用没见过其类型的留一类型折。

**动作：** 第零节表中全部方法各自选中的动作（相同物理动作只跑一次）。

**开发目标与"信息价值表"：**

| 编号 | 问题 | 报告内容 |
|---|---|---|
| T1 第一层能用 | 不看 controller，共享修正有没有用 | 学习双 η·进度阈值学出（不看 controller）相对只加安全投影、相对人定双 η·按进度切换的差，按类型与类型等权合并 |
| T2 在线信息 | 当前这一局的闭环进度，什么时候有用 | 主方法 − 第一层，分组报告：只加安全投影 ≥ 98%、90–98%、< 90% 的 controller；目标：≥ 98% 组的点估计 ≥ 0 且伤害数为 0，< 90% 组的 CI 下界 > −1pp |
| T3 离线信息 | 改进后的离线探测特征，什么时候有用 | "离线探测特征"那一层 − 主方法，分组报告：按族（学习型、优化型、搜索型）；按离线探测得到的卡法（探测中早停滞：停滞起始步 < 200；晚停滞：≥ 200；探测中不停滞）；按"选中 η 对与人定 η 对的距离"上下两半 |
| T4 阈值学出 | 阈值由学习决定有没有用 | 第一层 − 学习双 η·固定阈值 0.968（不看 controller）；选中 θ 的分布，按类型列出 |
| T5 触发设置按 state 选 | 有没有必要 | 主方法 − 单一触发设置消融 |
| T6 冻结前提 | 是否每个学习型类型都 ≥ 90% | 主方法在每个学习型类型上的成功率与 95% CI；逐项写明是否 ≥ 90%（点估计）；另报"离线探测特征"层的同一检查 |
| T7 参照 | 与跨type5 比 | 主方法 − 学习双 η·critic 判修不修·扩充提议 |

**信息价值表（交付的核心表之一）：** 行为"无 controller 信息 → 加在线进度 → 再加离线探测特征"三层，列为上述各分组，单元格为相邻两层的配对差与 95% CI。另附一列"完美类型信息上界"：在已评估的动作中，用同类其他实例按 state 选动作（交叉拟合）相对用其他类型选动作的差，作为"类型级 controller 信息最多还能带来多少"的参照。

**CI：** 按共同协议第四节，5000 次配对 bootstrap；类型等权时先类型、再 controller、再 state 成簇重抽（两个 seed 同簇）。unknown 按下界计，另报上界。

# 八、规模上限（开工时按精确 preflight 与等价复用写定）

| 部分 | 估计（复用前） |
|---|---|
| 训练 state 新增动作（122 × 48 × 9） | 约 53,000 条 |
| 离线探测第二版（122 × 16 × 2，各 700 步） | 约 3,900 条 |
| 新 state 评估（122 × 24 × 2 × 约 8 个不同动作） | 约 47,000 条 |
| 不看 controller 的时间表生成器重训（若启用） | 只有训练，无 rollout |

合计复用前约 10.4 万条；不卡的 controller 上，在线停滞触发动作大多不会触发，可按 4.2 的规则直接复用只加安全投影的结果，实际执行会明显更少。开工时按跨type5 记录的单条耗时估计总时长，写进开工记录。实现错误导致的重跑写进迭代日志，累计不超过 8,000 条。提交顺序：执行等价性测试 → 离线探测 → 训练 state 标签 → 训练与冻结 → 新 state 评估。

# 九、执行顺序

1. 确认开工前提 → 完整性审计（开始，含并行任务目录清单与 `squeue`）→ 复现跨type5 的 16 条记录（覆盖至少 3 个学习型类型、2 个模型预测控制类型，其中至少 4 条为切换时重查动作），逐位一致 → 执行等价性测试 → 第三节的 η 来源决定与开工记录（触发与阈值网格、抽样种子、新 state 种子、规模上限、各分组的定义）。
2. 离线探测第二版与特征。
3. 训练 state 标签。
4. 19 折训练（如启用，先重训不看 controller 的时间表生成器）→ 留一类型检验 → 冻结。
5. 新 state 选择并密封 → 标签 → T1–T7 与信息价值表（数值写入 JSON/CSV 并封存）。
6. 图与排版（非主线收尾，单独一步，用画图环境）→ 完整性审计（结束）→ 交付。

**失败处理（用户 2026-10-20 要求：不影响主线的问题不得让流程停下）：** 跨type5 中，覆盖度统计已经算完，只因出图时缺 matplotlib，协调器就整体停住约 8.5 小时，后面的新 state 评估一直没有提交，直到用户来问才发现。本轮把失败分三类处理：

| 类别 | 包括 | 处理 |
|---|---|---|
| 整体停下 | 写入了只读位置（源码保护被破坏）；共享 DB 规则被破坏；复现或执行等价性测试对全部类型都无法满足 | 停下报告。只有这三种情况可以整体停下 |
| 主线 | 复现与执行等价性测试、离线探测、训练 state 标签、模型训练与冻结、新 state 选择与评估、T1–T7 与信息价值表的数值 | 作业失败时先读日志定位原因。**基础设施原因**（节点故障、内存不足、Slurm 时限、被抢占、提交错误）：未完成的部分按已写定的案例与种子重新提交，已完成的记录保留；这不是"重跑已有记录"，也不是挑结果。**实现错误**：修正后只重跑受影响的部分，写进迭代日志，计入 8,000 条上限。**某个类型确实做不了**：记为缺口并写明原因，其余类型继续 |
| 非主线收尾 | 图、Markdown 排版、可选附表、视频 | 不得作为任何主线阶段的前置条件，也不得写进主线统计脚本：数值先写入 JSON/CSV 并封存，图与排版放在最后单独一步，从封存的文件生成。失败或缺包时写进 `GAPS.md`（缺什么、影响哪项交付），其余阶段照常继续，交付时如实列出。不得为此安装新包 |

**无人值守：** 调度脚本（协调器）必须自己执行上表：非主线失败记录后继续；基础设施失败自动重新提交未完成的部分（同一阶段最多 3 次，仍失败就按缺口处理）；不得因为缺一个非主线文件而退出。运行期间至少每 30 分钟更新一次 `STATUS.md`（当前阶段、已完成量、阻塞原因、已采取的处理）。交付之前保持监控：至少每 30 分钟查看一次协调器状态与 `squeue`，发现阻塞立即按上表处理，不要等用户来问。只要还有不依赖受阻部分的工作，就继续做。

"不重跑"的含义沿用共同协议：已有的同身份记录一律复用，unknown 一律保留、不重跑。它不禁止重新提交因基础设施失败而没有完成的作业。

# 十、结论映射

| 观察结果 | 论文中的结论 |
|---|---|
| T1：第一层在多数会卡的类型上显著优于只加安全投影 | "修正本身不依赖 controller 就能用"成立：共享的脱困结构可以只从 state 学出 |
| T2：≥ 98% 组不再受伤害，< 90% 组不损失 | 在线进度这一 controller 信息回答了"修不修、何时开始修"：不卡的 controller 不触发修正，卡住的 controller 被及时修正 |
| T3：离线特征只在某些分组为正 | 写明离线 controller 信息在哪些情况下有用（例如跨族、或学出的 η 对偏离共享结构时） |
| T3：离线特征在所有分组都约为 0 | 共享结构加在线进度已经足够；离线 controller 信息不是必需的，作为消融报告 |
| T4 为正 | 进度阈值也可以由学习决定，不需要人定的 0.968 |
| T6：每个学习型类型都 ≥ 90% | 达到用户确定的冻结前提；下一轮冻结设计，并在 3 个完全没碰过的类型上做最终检验 |
| T6：仍有学习型类型 < 90% | 列出这些类型与其失败归因（η 来源、触发、阈值），作为下一轮的改进对象 |
