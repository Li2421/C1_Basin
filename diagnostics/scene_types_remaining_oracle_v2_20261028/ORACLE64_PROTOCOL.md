# Oracle@64 追加协议

依据用户最新要求：原16组参数失败的初态继续搜到64组；找到解即停止；64组未找到成功即记本轮搜索失败，不再加预算。无 Generator、无训练、无 GPU。

对象是已冻结的七个 B family，各120个 controller×初态案例；另外保留原要求的放宽 Goal 参数盒 B3 同预算对照，共八项。每项使用同一个全局64点池，各案例不能另选更有利的池。保持前16点；B3保留已跑的第17..32点，再追加32个成对 Sobol 点。其他六族追加48个固定 Sobol 点。精确系数、种子、冻结时间、来源哈希见 ORACLE64_FROZEN.json。所有参数在执行新 rollout 前冻结，不用新结局调点。

旧数据去重：逐物理状态、精确 nominal、原安全语义和完整参数配置检查已有主池、范围消融及56点救援筛选结果；用旧 UID/原始记录直接参与查询，完整unknown同样保留。新命名空间不作为重复生成同语义 rollout 的理由。所有真正缺失候选由原 safety solver 执行，matched物理随机流、规划预算、整局时长和成功判据不变。新请求全量登记并 official preflight 后才提交。

按冻结顺序逐候选查询，首次成功则停止该案例的后续运行。第64点仍未成功则停止；异常计入64点有限预算，另报unknown类型，不改变任何已有标签。一个案例中首次成功的序号1..64，就是按本顺序找到成功所需候选组数。

必须报告：各 B 的 Oracle@16/@32/@64、首次成功序号在成功案例中的均值、全120案例截断查询数均值（失败按64）、原16失败队列中的新增成功数和新增实际 rollout 成本；逐类型/nominal分解；成功条件任务时间、配对共同成功时间及全队列截断任务时间分别统计。旧16点当年全部执行，因此“首次成功序号”不是旧实验实际耗费的 rollout 数。

本轮已看过原留出结果，属于事后预算扩展，不能冒充新独立验证。旧 Oracle@16 与维度结论不覆盖改写；Oracle@64单独出表。64点无解按用户要求结束为搜索失败，不宣称连续参数空间不存在成功 η。论文六项正式baseline只复用其已有冻结结果；三/四/五列属于内部比较。

18个CPU上限，单worker1CPU、BLAS1、GPU0。新增尝试有限上限20000，涵盖本阶段最大缺失集合和基础设施重试。原研究45000全局上限在本次显式64点扩展请求下不再作为拒绝新增请求的理由，旧消耗与本轮消耗分别如实记录。完整unknown不重跑；基础设施仅补未完成 UID。worker写journal，唯一协调者合并并读回；每30秒检查自身Slurm实际占用、保护事件和进度。
