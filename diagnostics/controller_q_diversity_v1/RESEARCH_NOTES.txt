Question: do within-scene and cross-scene transfer require different inputs?

The underlying target is Q(s, eta; controller, execution/environment settings).
An input may omit a variable when it is fixed throughout a within-scene task,
or recoverable from other observations. Cross-scene variation can invalidate
that simplification. A common complete representation can still serve both
tasks: separate input architectures are not theoretically required.
Input sufficiency does not imply that finite source data identify a transferable
mapping. An unseen value of a supplied constant is still an extrapolation if
there was no training variation in that constant.

Actual input audit:
 - Existing masked physical adapter retains agent/pair/map geometry, radius,
   and goal tolerance, but zeros all15 global channels.
 - This removes physical/task information as well as controller-related fields:
   max speed, dt, remaining time, horizon, margins, and monitor settings.
 - Toy maxspeed0.5, horizon850x0.05=42.5s;
   Ring maxspeed0.52, horizon700x0.05=35s.
 - Cache first-success censoring gives identical encoded inputs with different
   success-by-budget answers if the time budget is allowed to vary. This is a
   sufficiency counterexample over variable budgets, NOT proof of aliasing on
   the two/four fixed benchmark supports. Existing geometry may identify their
   fixed settings implicitly.
 - Restoring all existing physical/task global channels is tested without
   changing labels, fitting target normalization, or adding a scene ID.

Source/controller diagnosis:
 - Analytic family varies six parameters independently by outcome-blind LHS.
 - First64 TRAIN states: no-controller empirical MSE floor Toy0.231079;
   Ring conservative numerical-completion floor0.200745.
   These are finite-panel source diagnostics, not final generalization results.
 - Raw field queries recover all six analytic parameters in20/20 Ring input
   cases; Toy19/20 have normalized error<1%, one weak/saturated case ~5.2%.
   This excludes absent family parameters as the sole failure of that descriptor.
   It does not establish identifiability of arbitrary native Flow controllers,
   or of every compressed/clipped feature/model variant.
 - Rich concatenated field critics overfit despite informative inputs.
 - Bilinear physical/eta-conditioned coefficients of static nominal/contact
   query features improve SOURCE controller transfer. No simulation preview,
   future outcome, scene ID, or hidden controller weights enter the features.

What the evidence supports so far:
 1. Missing controller information matters when the controller actually varies.
 2. Merely supplying rich identifiable controller inputs does not solve learning.
 3. Useful controller diversity can improve transfer within known environments.
 4. This does not automatically transfer the state/controller/Q relationship
    across scene/execution distributions.
 5. Omitted task constants and unsupported geometric directions are real input
    limitations; tested repairs do not make them the uniquely established cause.
 We have not isolated geometry, safety, FF initialization, horizon, number of
 agents, and physical-state support into independent causal scene interventions.
 Therefore do not label any single one as the proven root cause of LOSO error.
